Scam Pattern
Ledger.

PatternLedger is a GenLayer Intelligent Contract that keeps a public list of how scams work, never the scam messages themselves. Before a pattern is stored, every validator asks its own AI model whether the summary identifies anyone and whether it describes a real scam, and the network only stores it when they agree. Everything below the explainer is read live from the contract by your browser.

How it works

A record is one scam pattern: the trick, in plain words. The same trick reported again, in other words, adds a sighting to the existing record instead of a second copy.

What it stores

  • A category, one of 8 fixed values (delivery, locked account, romance, job, prize, investment, impersonation, other).
  • Warning-sign codes, a subset of 16 fixed codes such as "urgency" or "asks for a code".
  • A summary of at most 200 characters: an abstract paraphrase of the trick.
  • A sighting count, first and last seen times (the transaction's time), and the newest 100 sightings with their codes.
  • The request key of each accepted submission, so a retry of the same report is answered without a second review.

What it never stores

  • The message itself, or any hash of it.
  • Who received it or who sent it: no user id, no phone number, no address. The only writer is the VERDICT relayer or the owner.
  • Anything with a digit, an "@", a currency sign, a link or a bare domain: refused before any AI is asked.
  • Refused reports: the transaction reverts, so nothing about it enters the ledger's state.

How validators decide

  1. Fixed rules first, no AI. Only the relayer or the owner may write. The codes and category must come from the fixed lists, the summary must be 200 characters or fewer, contain no instruction aimed at the reviewer, and pass the identifying-data screen (no digits, "@", currency signs, links or domains). Any failure reverts.
  2. The leader reviews. One validator asks its AI model three things about the summary: does it contain identifying data, is it a coherent scam pattern, and is it the same pattern as one of the stored records in the same category (up to the configured number, 10 by default, shown below).
  3. Every other validator re-checks independently. Each one runs the same review with its own model and accepts the leader's answer only if both yes/no answers match exactly, and, when the record would be stored, the same new-or-same decision and the same record id. Rewording does not matter; the decision does.
  4. Stored only on agreement. If the majority agrees that the summary identifies no one and is a coherent scam, the record is created or its sighting count goes up by one. Otherwise the transaction reverts with [REJECTED].

This is GenLayer's gl.vm.run_nondet_unsafe with a custom validator function (the agreement rule, the validator). A validator whose own AI call fails, or that receives a malformed leader answer, votes to disagree, so an error is never agreed into the ledger.

    What this does NOT prove

    • "Identifies no one" is the judgement of the validators' AI models plus a fixed screen. Models can be wrong; the fixed screen only catches digits, "@", currency signs, links and domains.
    • A refused report leaves no trace in the ledger's state, but the transaction and its inputs are still public on the network, like any transaction. That is why the relayer redacts before it submits.
    • A sighting count measures reports the relayer submitted, not how common a scam is in the world.
    • This is a testnet with no real value. The relayer writes on users' behalf, so the ledger trusts the relayer to submit only reports users opted in to.
