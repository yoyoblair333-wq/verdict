1 · A real trust problem, not a better LLM answer

When one company's AI settles a disagreement, both people must trust its model, prompt and servers, and neither can check or appeal the call. In VERDICT the leader runs a five-juror AI panel, and every validator re-runs that panel with its own model. The ruling is written only if the validators agree with the leader's result (_verdicts_agree in contracts/judge_router.py, run through gl.vm.run_nondet_unsafe). The loser can appeal to a 7-juror, then a 9-juror panel.

  • See it: the "Proof, live" panel on the home page reads a recorded Supreme Court ruling and shows how its validators voted, live from the network.
  • Full appeal ladder: case 1 went 5-0, then 7-0, then 9-0. Supreme Court tx 0xf417c0f6a1f40e9baaa3ca1a9c32c628d6bbdf969c384ceefd604be026fc1891.
  • A validator disagreed and the majority still held: case 2 appeal tx 0x9f26a7927297178492dd76f27a7cea87de03759ab3ac7770516a60b207f6fd18 (agree 3, disagree 1, idle 1).
  • The winner cannot block the loser's appeal: a revoke after the verdict was confirmed is refused on-chain, tx 0xbea18f58dea8eef3e671470c3f0412372927a954ee7b7e4bf4af8cc90689ef61 (FINALIZED with execution ERROR, as designed).
  • Second contract, same idea: PatternLedger stores a scam pattern only if validators agree it identifies no one. A summary with digits was refused on-chain, tx 0xc66ed87412db89f8b2fd651e29cc327080e709ecbdf2b214c23841cc1639643d. See the Scam Pattern Ledger section.

2 · Live or authoritative data

Honest answer: VERDICT's outcomes do not depend on real-world facts. The jurors judge only the two takes the parties submit, against a fixed rubric, so there is no outside data to fetch and none is fetched. The data the app does depend on, the contract state and each transaction's validator votes, is read live from the network by the visitor's own browser. Nothing on the pages is computed or cached by a VERDICT server.

  • Check: open the home page with the browser's network tab: cases come from gen_call and the proof panel from a transaction read, both to studio.genlayer.com/api.

3 · Complete source and accurate docs

  • One command from a fresh clone: git clone https://github.com/yoyoblair333-wq/verdict.git verdict && cd verdict && bash scripts/verify.sh. No keys, no network writes. It runs the contract tests, genvm-lint on both contracts, the relayer type check and tests, and the offline web tests, and ends with VERIFY: PASS. CI runs the same script on every push.
  • What it is, the problem, how to use it: README. Product spec: docs/SPEC.md. Threat model: docs/THREAT_MODEL.md. Decisions: docs/DECISIONS.md.
  • Deployed code = GitHub code: Try to rig it hashes the deployed code and the GitHub source in your browser. The home page and the ledger section show the same check for both contracts.

4 · The frontend calls the contract through the full transaction lifecycle

  • Do it yourself: on the home page, Try it on testnet, click "Fill in a sample case", tick the two boxes and "Send to the jury". Your browser makes a throwaway testnet account and signs open_case_package, judge and confirm_verdict itself. The status rail follows the real transaction status (submitted, jury scoring, network checking, finalized), then the verdict is read back from the contract. About 2 to 4 minutes.
  • A recorded browser-signed case (case 4, no relayer): open 0x58ae3f80a9ec07be66de86c1a3ed28f5a72c50bd751ae479c218b50f09882206, judge 0xf5ec127771d95ab09abb57b770287379b6ddc096e0c70c42105cfc6fb18f18df, confirm 0x0aebc775fa868914ee9cb383e93b90d70bcc47e5d6481d31e76cbfabd4ed602a.
  • Watch it: 90-second demo video, a screen recording of the live app.

5 · Different from boilerplate, with a path to continued use

  • Not one LLM call: named juror personas, tiered panels of 5, 7 and 9, a custom validator that checks the leader's verdict (not just its format), a confirmed verdict that cannot be revoked to block the loser's appeal, provenance labels for who opened a case, and a second contract (PatternLedger) whose validators judge privacy and dedup.
  • Owner and relayer are separate keys: both contracts were deployed from the owner's own wallet; the relayer can run cases but cannot pause, re-key or take ownership.
  • Ways to keep using it: a relayer service with a REST API, documented in the README section "Use VERDICT from your app". Plans are listed there and labelled as plans.

What this does not show yet

  • No public users yet: every case on-chain is a test case.
